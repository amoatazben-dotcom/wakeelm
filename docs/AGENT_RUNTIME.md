# Agent runtime

Project detail → intelligent task → READ_ONLY, SUGGEST or WORKSPACE → task text. Submission commits a QUEUED job immediately. A separate asyncio worker reads the durable SQL queue; Telegram/FSM locks never cover agent execution. Status/cancel callbacks remain available while the worker awaits the provider or sandbox. Recent jobs, change history, diff downloads, validation results and approval/reject buttons are available in Arabic and English.

`AgentPlanner` builds bounded context with provenance and hashes. Proven tool metadata enables native OpenAI function calls (names use `__` on the wire); unknown support uses strict JSON `AgentPlan`. The selected provider/model must belong to the user and remain enabled. Extra fields, invalid tools/arguments and oversized plans fail closed. Files/tool results are expressly untrusted instructions. Provider calls use the existing DNS-pinned gateway; no direct network tool is exposed to the model.

A plan contains goal, ordered ToolRequest steps, risk, complete and optional answer. `complete=false` triggers bounded follow-up planning with the last three bounded observations. A final answer with no actions requires complete=true and nonempty answer. Plans, requests and answers are encrypted; public plan JSON contains tool names/risk only. Tool logs/step inputs redact patch text, queries, provider credentials and output. Usage counters use provider-reported tokens when available.

States: QUEUED → PLANNING → RUNNING → WAITING_APPROVAL → QUEUED/resume, or COMPLETED/FAILED/CANCELLED/LIMIT_REACHED. Resume decrypts the same plan/current step and does not repeat completed paid calls or edits. Cancel sets a Redis flag; running tasks use CANCEL_REQUESTED until the worker acknowledges, keeping deletion/reindex locked. A paused/queued task can be cancelled immediately. Cancellation is checked before and after tools and during container execution; provider calls finish or hit their bounded deadline. Cancellation during file writes compensates the batch if interrupted; already completed batches remain inspectable/restorable.

Default limits: 12 steps, 20 executed tools, 2 replans, 1 repair, 300 active seconds, 60 seconds per command, 32 KB output. Waiting for approval does not consume active time. Invalid plans use the same replan budget. Failed commands may trigger one repair with fresh observed hashes and a fresh approval for the next command. Failed validation, exhausted budgets, provider errors and unknown actions stop safely.

One Redis worker lease is renewed by token-checked Lua; standby replicas do not recover live jobs. One workspace execution lock serializes jobs; edit locks protect batches. SQL row locks bind approvals/submissions and SKIP LOCKED claims the queue. Use one application worker/shared persistent volume in this stage; local filesystem workspaces are not distributed storage.

On restart, interrupted jobs enter RECOVERING. APPLYING snapshots are restored only if current hashes match the original/applied alternatives; conflicts require review. Jobs then fail with WORKER_INTERRUPTED rather than replaying paid requests. Expired approvals are persisted as EXPIRED and the paused job fails. `/ready` also reports worker task health when the bot is enabled.

COMPLETED means the planned batch finished and file/hash/Python syntax checks passed. It does not prove the user goal semantically. The report marks goal comparison REVIEW_REQUIRED and tests NOT_RUN unless command runs exist. Inspect diffs and test results. Other-language syntax requires the configured validator image/toolchain.
