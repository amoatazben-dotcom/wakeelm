# Git security boundary

`ControlledGitService` implements the narrow asynchronous `GitService` protocol in Python around trusted Git argv. The model cannot provide shell commands, raw git flags, remote URLs, credential helpers, force, merge, reset, hooks or arbitrary subprocess execution. Ref/path parsing rejects option injection, traversal, `.git`, unsafe refs and non-agent write branches. Default/main/master and remotely protected branches fail closed.

Git runs with a minimal environment, fixed private HOME, no system/global config, empty credential helper, empty fixed hooks, disabled fsmonitor/textconv/external diff, fsck, no submodule recursion and no LFS smudge. Only canonical `https://github.com/owner/repo.git` origins are accepted; no redirects or persisted credentials. Local metadata config has a key allowlist and its worktree is verified against the owned root. Askpass reads a short-lived per-process token from a dedicated environment variable and the launcher/helper contain no token. Neither project files nor validation containers receive that environment.

Linux Git processes have wall-clock, output, address-space, CPU and file-size limits. A periodic monitor enforces total repository metadata bytes even during silent fetches. Process groups are killed on timeout/limit/cancellation. Git never executes project hooks/scripts as validation; project execution remains in the Stage 4 isolated runner. Git itself is trusted host software and is not a general container sandbox.

Secret/artifact checks inspect exact changed paths before commit and again before push. Credential files, token patterns/private keys, large files and generated/build/archive/database artifacts are denied. Findings contain paths/categories only. Detection is conservative and heuristic: arbitrary unlabeled secrets may evade patterns, so repository reviews remain necessary. Deleted content is not republished. `.gitignore` is respected; ignored files are not added by commit.

`GITHUB_PUSH_CI_REVIEWED=false` blocks publishing before approval. The operator must review repository workflows and downstream CI to ensure `agent/*` pushes cannot trigger production deployments before setting it true. Changes to `.github/workflows/*` remain blocked at push. A normal Git push may trigger existing repository workflows; GitHub supplies no universal way to suppress them. No workflow/deployment API is available, and the flag is an operator attestation, not automatic proof of every indirect workflow's behavior.

App installation tokens are scoped to the selected repository. Fine-grained PAT rights cannot be reduced by the client; scope them at creation. There is no production-secret inheritance, global per-user credential reuse or main-branch write bypass. Approvals are exact snapshots, not blanket authorization.
