# Security boundaries

* Credentials use Fernet authenticated encryption. The master key comes from environment configuration, not the database/source. Token hints reveal at most four trailing characters for tokens of length eight or more. Short secrets are fully masked. Rotate the master key only with a planned decrypt/re-encrypt migration; changing it directly breaks existing credentials.
* Private Telegram chats only. Token/header messages are deleted best-effort; Telegram delivery itself is outside this service's storage boundary. Deletion can fail due to Telegram permissions/age, so users should remove remaining messages. Redis FSM credentials are encrypted and expire after 30 minutes. Never share credentials through group chats.
* User ownership is enforced in repository/services, independent of callback IDs. Provider/model deletion is limited to the user's configuration and requires a confirmation stored in their isolated FSM. It cannot execute DDL or server shell commands. Parameterized SQLAlchemy queries prevent SQL injection. `is_active` provides the initial account permission boundary.
* Only HTTP/HTTPS public destinations are permitted. DNS answers must all be globally routable and not reserved/multicast. Localhost, private, link-local, loopback, IPv4-mapped private IPv6, shared address space, Railway internal names and cloud metadata addresses are blocked. Query/fragment/userinfo URLs are rejected. DNS addresses are validated again at connection resolution and handed directly to aiohttp's connector; original hostname is kept for TLS validation/SNI. There are no trusted internal exceptions in Stage 2.
* Redirects are disabled. Endpoints are fixed `/models`, `/v1/models`, and `/chat/completions`. TLS verification stays enabled. Connections have a five-second connect budget, 15-second read budget and configurable total deadline (default 30 seconds per request). Compressed responses are rejected and identity encoding is requested to avoid decompression bombs. Default payload cap is 2 MB and discovery cap 1,000 models. HTTP is accepted for compatibility and HTTPS is recommended; public endpoint ports are restricted to 80/443 in this version.
* Secret custom headers are encrypted/scoped to the provider and never displayed. Host, content length, transfer encoding, connection and proxy authorization are blocked. Invalid header characters/newlines are rejected.
* Logs allowlist structured fields. HTTP/Telegram library logs that can contain request URLs are disabled. Provider exception text, stack traces, Authorization and raw metadata are never logged or returned. Audits allowlist status/count/language metadata. Do not enable SQL echo, debug HTTP logging or external body capture in production.
* Redis enforces per-user action cooldowns, discovery cooldowns/locks, and per-user/per-model test cooldowns. Discovery failures never lead to automatic completion testing. Model test confirmation is mandatory. POST requests are never automatically retried.
* Webhooks require HTTPS configuration and constant-time checking of `X-Telegram-Bot-Api-Secret-Token`. Requests are limited to 1 MB, schema validated, deduplicated in Redis and isolated per user. In-progress duplicate deliveries receive 503 to allow retry. Protect PostgreSQL/Redis with private networking/authentication and maintain backups.

Stage 3/4 add descriptor-based no-follow paths, bounded archive extraction, ownership-scoped workspaces/search/chunks, encrypted chunk/plan/snapshot/diff/output storage, strict registered tools, mode policy, exact hash edits, persisted expiring approvals, bounded loops and a separate network-disabled container runner. See TOOL_SECURITY.md, APPROVALS.md and SANDBOX.md for enforcement and tested limits.

Deferred: external review, encryption-key rotation tooling, usage/cost quotas, VM-level isolation and an authenticated hosted validation worker for Railway. Model narrative accuracy and semantic goal completion still require human review. Use a private persistent storage volume and protect the database/master key; working source files are plaintext on disk with private permissions.

## GitHub and MCP

See GIT_SECURITY.md and MCP_SECURITY.md for branch, approval, SSRF, untrusted-output and credential boundaries. GitHub App user access is checked against installation repositories before a repository-scoped installation token is minted. MCP tools default disabled and require operator-reviewed fingerprints; high-risk writes require fresh exact approvals. OAuth uses one-use state/tickets, PKCE S256, nonce cookies and issuer/resource/redirect binding. Signed GitHub webhooks are idempotent. Integration job payloads are encrypted and cleared on terminal execution/recovery; inactive users cannot run queued work.

Start command disables query access logs; configure proxy logs similarly. A normal agent-branch Git push can execute existing repository workflows, so publishing is blocked until GITHUB_PUSH_CI_REVIEWED is explicitly enabled after production isolation review. Heuristic secret scanning is not a guarantee for arbitrary unknown secrets.

## Stage 7/8 boundaries

Memory excludes known provider/GitHub/MCP secrets, encrypts contents and proves user/workspace/job ownership. Required model capabilities need verified/provider-reported evidence. Specialist tool roles cannot bypass existing mode/approval/hash policy. Quotas and unknown-price reservations are durable server decisions; fallback counts against job budgets. External write intent receipts prevent automatic replay after uncertain results.

Admin requires configured OIDC signatures/issuer/audience/expiry/nonce and MFA, short secure HttpOnly sessions, exact Origin + CSRF on cookie writes, separately authorized roles and immutable audit. CORS is same-origin, CSP forbids third-party scripts/frames, body and per-class rate limits are bounded. Emergency global stops cannot be scoped to a partial rollout. Versioned encryption permits controlled offline key rotation. Dependency/SAST/source/history/container evidence is retained; unresolved image findings are not silently suppressed.
